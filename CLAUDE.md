# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Defog: a browser-only tool that reads a Fog of World `Sync/` folder (or backup .zip) and overlays visited ground on a Leaflet map, then plans/suggests routes that defog the most new area. The fog data never leaves the browser; only bounding boxes go to Overpass and tile numbers to the elevation tile host (see README "Privacy" before adding any network call).

## Running and deploying

A bench test loads a `.ts` module with Node's own type stripping (erasable syntax only: no enums, namespaces or constructor parameter properties; relative imports name the `.ts` file), so the repo root still has no package manager.

- No GitHub Pages site: `app/` ships only inside the phone app in `mobile/` (bundled into `generated/web.ts` by `pnpm generate`).
- `Sync/` (personal location history) is gitignored: never commit it or anything derived from it.
- Third-party libs are vendored in `app/vendor/`; there is nothing to install.
- `watch/` is the Wear OS watch app: a one-time import of GlanceMap (ADR 0009), its own Gradle project, application id `codes.madera.crossfog.watch`. Build and test: in `watch/`, `./gradlew :app:assembleDebug :app:testDebugUnitTest` (JDK 21, `ANDROID_HOME` set; the build reads the git SHA, so it must run inside a git checkout). Not part of `pnpm verify`. `link/` is the Kotlin module shared by the phone app and `watch/` (ADR 0009, #407): both Gradle builds include it (`watch/settings.gradle.kts`, and `mobile/plugins/withLinkProject.cjs` for the generated phone project), the phone's `pnpm test:android` runs `:link:test`, and `link/README.md` says what may go in it. ## Architecture

Every `.js` file in `app/src/` is a plain IIFE that hangs its API on `window` (e.g. `RouteTool`, `HistoryPanel`) and has no imports: **load order in `app/index.html` is the dependency graph**, so a new file must be added there after what it uses and before `main.js`. A `.ts` file is a module with real exports. `src/engine.ts` is the one `.ts` script tag (#408): it imports every converted module (`parser.ts`, `md5.ts`, `unzip.ts`, `fogWriter.ts`, `reveal.ts`, `overpass.ts`, `tileStore.ts`, `streetCache.ts`, `sha256.ts`, `fogGain.ts`) and assigns what the IIFEs need as window globals (`FogParser`, `MD5`, `FogZip`, `FogWriter`, `Reveal`, `Overpass`, `TileStore`, `StreetCache`, `Sha256`, `FogGain`; `pageGlobals.ts` builds the first eight: `FogParser`, `MD5`, `Reveal` and `StreetCache` are copies of their module's exported object, `FogWriter`, `FogZip` and `TileStore` are rebuilt there around the page's pako and IndexedDB so a new member of any of them is added in `pageGlobals.ts` too, `Overpass` is the module's own object (its test hooks are read from it) and `pageGlobals.ts` binds the window it reads `fetch`, `navigator.onLine` and `crossfogNextgisKey` from with `bindOverpassHost` (module state, so the last window given wins), and `engine.ts` adds the other two), and `mobile/scripts/web/bundleModule.ts` (esbuild, one IIFE, so one copy of each module) inlines it where the tag is, so the files below the tag read those globals as before and the CSP hashes cover the bundled text like any inline script. A converted module reads no page global when it loads or when it is called (it gets what it needs as arguments; platform built-ins such as `TextEncoder` are fine); the page globals the engine's files use (pako, IndexedDB, `fetch`, `navigator`, the NextGIS key) are looked up on the window `pageGlobals.ts` is given (`globalThis` from `engine.ts`, the test window from the test loaders) each time `FogZip.unzip`, `FogWriter.writeSync`, `TileStore.open` or an `Overpass` call runs, so the key is still read when a post is made and may arrive after the scripts ran, and `unzip.ts` and `fogWriter.ts` take `inflateRaw`, `deflate` and `inflate` in their `opts`, required, and the bundle step fails the build when an input comes from outside `app/src/`, which the host scan reads. The phone's vitest, `tsc` (through the tests' imports), biome (`pnpm lint` adds `../app/src/*.ts`) and knip (which follows the tests' import) see the same files; a bench test requires `bench/lib/host.js` (the Node global as `window`, and the Leaflet stub as `L`) and then `engine.ts`, and no module is listed anywhere else.

Data flow:
- `unzip.ts` / `parser.ts`: Sync tiles (zlib) -> `FogMap` of visited cells. Fog grid is 2^22 cells wide, 1 cell = 1 px at map zoom 14; `parser.ts` also owns the cell <-> lng/lat math everything else uses.
- `parser.ts` also keeps what a writer needs: `Tile.blockExtra(idx)` / `Tile.blocks()` hand out each block's bitmap and its 3 extra bytes (10 region bits + checksum `2*popcount+1`), and `FogMap` has an overlay of cells the app added (`addCells(Int32Array of [cx, cy] pairs) -> number new`, `clearOverlay()`), `version` (bumped by `addTile`, `clearOverlay`, and `addCells` only when it adds a cell), `totalVisited()`, and `blocks()` (every non-empty block, overlay ORed into the imported block). `addTile` throws (`tile <id>: ...`, the map unchanged) for a body shorter than its header or with a block index past the blocks stored (trailing bytes are fine), and a second copy of a tile replaces the first (`tileCount` counts distinct tiles); `parseTileId` reads a one-digit id's 6-character name. `FogParser.FORMAT` (frozen: `FILENAME_MASK1`, `TILE_WIDTH`, `TILE_HEADER_SIZE`, `BLOCK_BITMAP_SIZE`, `BLOCK_SIZE`, `blockKey`, `popcount`) is the Sync format the writer shares. `hasFog()` (an import loaded, or any overlay cell) is the one test for "there is fog" (`main.js`, `fogGain.ts`'s `computeGain` and `newness`), not `tileCount`; `isVisitedCell`, `countVisitedInCellRect` and `latLngBounds` include the overlay; `tileCount` still counts imported tiles only.
- `sha256.ts`: a module exporting `hex(string)` (the page's `Sha256.hex`, assigned by `engine.ts`), SHA-256 of the string's UTF-8 bytes as 64 lowercase hex digits (FIPS 180-4, written out because SubtleCrypto is async and needs a secure context); a route's `revision` is this hash of its GPX, the same value the phone (`gpxRevision`) and `link/` (`Revision.of`) compute, pinned to `link/`'s test vectors by `bench/sha256.test.js` (which `require`s the `.ts` file) and `mobile/test/unit/revision.test.ts` (which imports it and compares it with `gpxRevision`). Load order: before `history.js`.
- `fogGain.ts`: a module exporting `createFogGain({fogMap, worldCells, lngLatToCell})` (the page's `FogGain.create`), `distanceM` and `DEFOG_HALF_M` (15 m, the assumed half-width of the corridor Fog of World clears). It returns `cellIsNew(lon, lat)` (no visited cell in the corridor), `corridorNewFrac(lon, lat)` (the still-fogged share of the stamp), `computeGain(coords) -> {area, newPct} | null` (null without fog or with fewer than 2 points), `newness({lat, lng})` (the never-visited share within ~100 m, 1 with no fog) and `cellMetersAt(lat)`. Route length is `distanceM`, the haversine of Leaflet's `LatLng.distanceTo` step for step, pinned to the vendored `app/vendor/leaflet.js` to the last digit by `mobile/test/adapter/fogGainDistance.test.ts`. `bench/fog-gain.test.js` covers the rest. Load order: `engine.ts` loads before `main.js`; `suggest.ts` imports it.
- `md5.ts` / `fogWriter.ts`: `MD5.hex` and `FogWriter` (`tileName(id)`, `writeTile(blocks)`, `writeSync(fogMap, {deflate, inflate}) -> [{name, bytes}]`), Fog of World's Sync format. Imported blocks keep their region bits, new blocks get region 0, empty blocks and tiles are never written. `tileName` throws a RangeError for an id outside `[0, 512²)`, `writeTile` for a bitmap that is not 512 bytes, a position outside 0..127, `extra` not 3 bytes or a position given twice; `writeSync` reads every file back before handing it out (it inflates to the tile written, its name parses to its id, every block's checksum holds) and throws `tile <id>: ...` otherwise; `fogWriter.ts` itself needs `deflate` and `inflate` in `opts`; the page's `FogWriter.writeSync` (from `pageGlobals.ts`) defaults `deflate` and `inflate` to `window.pako`'s at call time (the bench sets `global.pako`, the phone tests pass fflate) and throws its two messages (one for a missing deflate, one for a missing inflate; pinned word for word by `bench/fog-writer.test.js`) when `window.pako` lacks it. `md5.ts` writes RFC 1321's table out rather than computing it with `Math.sin`. `bench/fixtures/fow/` holds two tiles Fog of World wrote (from Fog Machine, MIT) that must round-trip byte for byte. The default `deflate` is `window.pako.deflate` at level 5, from `vendor/pako.min.js`, the one full pako 2.1.0 build (`deflate`, `inflate` and `inflateRaw`; sha256 `ede2693a4a6a5126b9d35669062b358ecab6ae7b9b86a1cf302feb45a8514907`, the file `dist/pako.min.js` of the npm package); `bench/fog-writer.test.js` checks that the two Fog of World tiles come back byte for byte through `writeSync`'s defaults. Node's own `zlib` is Chromium's fork and does not reproduce Fog of World's level-5 bytes; pako does. Load order: the engine script after the pako tag, before `fowExport.js`.
- `reveal.ts`: `Reveal.reveal(track, rules) -> Int32Array` of `[cx, cy]` pairs (sorted by `cx` then `cy`, unique), the cells a recorded track explores; `Reveal.RULES` is the versioned rule set (`version`, `maxAccuracyM`, `maxGapS`, `maxGapM`, `halfWidthM`; untuned placeholder numbers; every field but `version` must be a finite number >= 0). Pure: points with a non-finite `t`, `lat` or `lon` are skipped, points with a worse accuracy are dropped (a numeric string compares as its number, a missing accuracy keeps the point), consecutive points join into a segment only within the time and distance gaps (an antimeridian crossing is a gap, and a gap leaves each end as its own disc, so nothing between the ends is revealed unless they are closer than `2 * halfWidthM`), and a cell is revealed when its centre lies within `halfWidthM` of a segment or an isolated point. Latitudes clamp to ±85.0511; a disc at the antimeridian wraps to the other side of the grid. Load order: in `engine.ts`.
- `fogLayer.js`: Leaflet GridLayer painting the fog (paints one side, composites with a CSS blend mode on the pane).
- `overpass.ts`: `Overpass.post`, the only Overpass caller: endpoints in a user-set order (by default NextGIS's `https://overpass.nextgis.com/<key>/api/interpreter`, then overpass-api.de; NextGIS exists only when `window.crossfogNextgisKey` is a non-empty string, read at each post because the phone app may set it after the page's scripts ran, so with no key, overpass-api.de is asked alone; `Overpass.has(name)`, which `main.js` checks to offer NextGIS in its endpoint choice, again on the `crossfog-nextgis-key` window event the phone app's injected script fires; `main.js` passes no order unless the user stored one it can honour, so NextGIS still goes first when the key is set late; a stored order naming an endpoint that does not exist reads as the default whole; no message or log names the key or the keyed URL, and tests use only a made-up key), at most 4 requests in flight on NextGIS and 2 on overpass-api.de, every caller's together (`Overpass.cap()`, the cap of the first endpoint that exists and is not on hold, or of the first when all are, is how many `overpassFetch` keeps open, so a held NextGIS does not leave posts queued for overpass-api.de's 2 slots): a post waits for a slot on the endpoint it is about to try, a fallback for one on the next, and one that waited is not sent where a hold was set meanwhile; a hold is never cut short by a request that was open beside the one that earned it, and requests open together that stall together count as one stall. An endpoint is abandoned when no response headers arrive within 90 s (overpass-api.de sends nothing while a request waits in its queue, see FIRST_BYTE_MS in `overpass.ts`) or the whole answer is not in within 120 s; such a stall holds it 30 s, or 10 min from the third stall in a row with no finished answer in between; it is held at least 30 s (longer when Retry-After says so) after a 429 or a rejected fetch (network error, CORS-hidden answer), except that NextGIS is held 10 min from its third rejected fetch in a row with no finished answer between (a finished answer, any status but a stall, resets the count; requests open together that are rejected together count once, as stalls do; one `console.warn` line per streak, `[overpass] endpoint rejected <name> <n> fetches in a row; held 10 min`, never the URL or key; the reason stays `offline`), and held 1 h after a 406 (the day's share used up; longer when Retry-After says so); a 401, 403 or 404 from NextGIS (a revoked or mistyped key, which NextGIS may answer with a 404; overpass-api.de has no key, so there each is any other non-2xx answer) holds it 1 h with reason `server` and `console.warn`s `[overpass] endpoint answered <name> <status>` once per endpoint name (never the URL, which holds the key; a 404 that arrives without CORS headers is a rejected fetch in the WebView, so it reads as the 30 s network hold with no log); any other non-2xx answer, or a 200 whose body is not JSON, or is JSON but not an object (`null`, a string, a number), moves on to the next endpoint with no hold. A failed post carries `err.reason` (`blocked`, `busy`, `stalled`, `offline`, `server`, in that precedence, never server text; the precedence ranks the endpoints this post asked, and an endpoint skipped as held speaks only when none was asked, so a NextGIS 502 during overpass-api.de's 406 hour is `busy` and waited out, and `blocked` needs a 406 in this post or every endpoint held with a block among them; a browser that reports offline adds `offline` to what this post asked, and when no endpoint was asked it replaces the holds' reasons, since they date from earlier posts, while `retryAt` still reports the holds) and `err.retryAt` only when every endpoint is held (the earliest hold's end, the earliest block's when the reason is `blocked`); the error thrown is a copy of the one that earned the reason, which it carries as `cause` (a held endpoint keeps the error of its hold; every post throws its own copy, so concurrent posts never rewrite each other's `reason` and `retryAt`), so a 406 on one endpoint in the same post is not reported as the next one's silence. `Overpass.post(body, {stale})`: `stale()` true before a request goes out (checked before each endpoint, every `STALE_POLL_MS` (1 s, on `Overpass._setTimeout`) while the post waits for a slot, and again once its slot is free) sends nothing, passes the slot on and rejects with reason `superseded`, so a replaced run's posts still waiting for a slot do not go out ahead of the run that replaced it; a throw from `stale()` once the slot is free rejects as itself, the slot given back. `StreetIndex.rectQuery` asks `[timeout:25]` so the server ends a query by 25 s of running; overpass-api.de sends nothing until then, so queue plus run must fit the 90 s first-byte guard, and a request that does not is a stall. Built in `engine.ts`; `streets.ts` imports it.
- `streetMessages.ts`: `StreetMessages.describe(err, now)` and `progress({done, total, waitUntil}, now)` (the street index's own report object) (while a busy server is waited out: "The street servers are busy. Trying again in about N s… (D of T)", the wait rounded like `retryAt`), pure (no DOM, no Leaflet), what the suggestion card and the route hint say about a street download. `describe` reads only `err.reason` (`busy`, `blocked`, `stalled`, `offline`, `streets-partial`; `server`, anything else or nothing gets the generic text), `done`, `total`, `retryAt` (rounded up to 10 s, in minutes past two) and, for `streets-partial`, `err.cause.reason`; it never prints `err.message` or anything from the server, which can hold a remark or a tile number. `bench/street-messages.test.js` also checks that `main.js` words `streets-fetch` only through it. Built in `engine.ts`, so before `main.js`; a bench test gets it from the engine, though suggest code only emits counts and reasons (`main.js` words them).
- `streets.ts`: `StreetIndex` (a constructor function, and `window.StreetIndex` is that very function, not a copy: other files construct it and call its statics) composes `streetStore.ts` and `streetDownload.ts` on one object: the store's fields and methods are on its prototype chain (so `ways`, `version`, `covered`, `newAreaM2`, `snapPoint` and the `_read`, `_addWay`, `_anchor`, `_cover` that tests call are read off the index itself), `index.download` is the download (`ensureRects` of the index calls `index.download.ensureRects`; `index.download.idle()` is true when no tile is in flight, the one read the tests have of the in-flight registry), and the download reaches the store only through `StreetSeam` (`holds`, `anchor`, `read`, `cover`, `protect`), whose calls go to the index's own methods at each use, so a method replaced on an index is heard. `StreetIndex.rectQuery` and `StreetIndex.splitAnswer` are read off the constructor when a request is built or answered, so replacing them there is heard. The statics of the other files are `streetGrid.ts`'s and `streetDownload.ts`'s own functions. Shared by `planner.ts`, `suggest.ts` and `routeLocal.ts`.
- `streetGrid.ts`: the fixed 0.025° tile grid (`tilesCovering`, `tileBounds`; `tileId(t)` is the `"x:y"` key of a tile in every Map and Set; `streetCache.ts` keeps its own persisted key format)
- `streetInFlight.ts`: the tiles a running download is asking for, so a later run waits for one instead of asking again. `createInFlight()` -> `{of(id), idle(), forRun()}`; `forRun()` hands one run `{claim(tiles), release(id, via?)}`: a release settles the entry's promise once with what the source said of the tile (`{cached: true}` from the street cache; nothing when the run gave it up), and only the run that claimed an entry can take it out, so a run's release never removes the entry a later run set up for the same tile. Tested alone by `bench/street-in-flight.test.js`. `streetDownload.ts` is its only user; `index.download.idle()` is `idle()`.
- `streetDownload.ts`: how tiles arrive. `StreetIndex` fetches OSM ways through an injected street source (`opts.fetchStreets(tiles, onTile, opts) -> Map "x:y" -> answer`, calling `onTile(tile, answer, via?)` as each tile arrives (`via` `{cached: true}` for an answer the street cache held); `opts` is `{now, wait, stale}`; default `StreetIndex.overpassFetch`: one Overpass request per street block (the 2x2 group of grid tiles; "street block" in comments, never a bare "block", which is Fog of World's bitmap block), street blocks in the order of their nearest missing tile, never two in one request, asked as the missing tiles' box when they fill a rectangle and else as the whole street block's box, its unasked tiles handed to `onTile` like the others (so the street cache stores it; `ensureRects` reads and covers it but does not count it), up to `Overpass.cap()` requests open at once, each answer split into `onTile` as it lands (the bench does not use it: `bench/lib/tileFetch.js` asks the run's single rect); one busy schedule per run: a `busy` failure puts its street block back in the queue and waits `BUSY_RETRY_MS` 15/30/60 s (or its `retryAt` when later), busy answers while a wait is set are the same step, nothing new is sent until the wait ends, the open requests carry on, and `opts.wait(until) -> false to give up` is called only once none is open; an answer that lands while no wait is set restarts the count (one beside a busy answer, with a wait already set, does not); a busy answer past the third wait ends the count only once the requests open with it have finished and none was answered (if one was, the count restarts with that busy as its first 15 s step, so the outcome does not hang on which answer lands first); `opts.stale` goes to `Overpass.post`, so a replaced run's posts still waiting for a slot are not sent; the ended count, any other failure, a refused wait or a throw from `onTile` or `opts.wait` sends nothing new, lets the open requests finish and hand their tiles to `onTile`, then rejects with the failure that stopped it (for a refused wait or an ended count, the last busy answer)). `ensureRects(rects, {onProgress, deadlineMs, holdAs})` asks for the missing tiles nearest the rects' centre first (a tile an earlier normal run is still asking for is in the in-flight registry (`streetInFlight.ts`) and waited for instead of asked again; one that run gives up, failing or replaced, is asked again unless another waiting run already asks or read it, so of several waiting runs one asks; a replaced run waiting only on such tiles rejects `superseded` when the next one lands, and the run bringing them carries on), merges each tile as it arrives (`version` bumps per tile), reports `{done, total}` (`total` is every tile under the rects, and the tiles the index already holds count as `done` from the first report, so a retry shows the same N as the run before it), and stops asking once `RUN_DEADLINE_MS` (20 min) has passed on the `opts.now` clock (default `Date.now`); a busy wait checks `stale()` every `STALE_POLL_MS` (1 s; its deadline is checked before it starts), and a run waiting for a tile another run asks for checks `stale()` and the deadline as often, both on `opts.every` (`(fn, ms) -> stop`, default `setInterval`), so a replaced run lets go of its tiles within a second, and a shared tile not in by the deadline rejects with cause `stalled`; its `wait` refuses a busy wait that would end past the deadline, returns at once with no report when the wait is already over (open requests outlasted it), else reports `{done, total, waitUntil}`, sleeps (`opts.sleep`, default `setTimeout`) and reports `{done, total}` again; `ensureRects(..., {stale})`: once `stale()` is true the run asks for nothing further (checked before the source, at each tile but the last, around each wait and in `Overpass.post` before each request, and again once the source returns, so a run replaced while its last request was open rejects too) and rejects with a download error whose cause reason is `superseded`, so a replaced suggestion or route edit does not queue the next one behind it; a failed run keeps what arrived and rejects with `StreetIndex.downloadError(done, total, cause, arrived)`: `done`, `total`, `cause`, `reason` (`streets-partial` only when that run downloaded a tile, `arrived` being the tiles it read that the network brought: what the street source hands `onTile` with `{cached: true}` (the street cache), tiles the index already held and a shared tile the earlier run read from the cache do not count, a shared tile it downloaded and an answer in the source's Map alone do; else the cause's, so an offline run in a partly cached area says offline; a server remark in a 200, a source that returns something that is neither a Map nor nothing, an answer `splitAnswer` finds unusable (not an object, no `elements` list, no count marker, the one `rectQuery` ends the geometry with: a cut answer, never stored as covered) and a tile the source left out are `server`, with a fixed message that never carries the remark; `splitAnswer` puts a way in every requested tile one of its segments touches, not only a tile holding a vertex, and the first tile when none does; a way whose geometry is no list or holds a null or non-finite vertex is left out, so it is not stored, and the rest of the answer is read) and the cause's `retryAt`; `StreetIndex.downloadFacts(err)` is the part a caller passes on (`{reason, done, total, retryAt, cause: {reason}}`, never the message). A throw from `onTile` passes through the sources unchanged; `ensureRects` wraps its own deadline throw as a download error and rejects a bug as itself (also one the source wrapped in a download error whose cause has no street reason, even when every tile arrived; a failure that landed first in a run since replaced is `superseded`): one thrown while reading a tile, by the caller's `onProgress` or `sleep` during a busy wait, while building or starting a request or in an answer's handler (it stops new sends, the open requests finish and hand their tiles to `onTile`, then the run rejects with it, so it never hangs), or any throw from the source that carries no street reason (`busy`, `blocked`, `stalled`, `offline`, `server`, `superseded`; `overpassFetch` likewise passes such an error through unwrapped); of several bugs in one run the first is the rejection, so the class a caller logs is the first's; `StreetIndex.isDownloadError(e)` (numeric `done` and `total`) tells a download error from a bug, `StreetIndex.isSuperseded(e)` a download error whose cause reason is `superseded` (the one failure that is neither shown nor logged; a download failure of a stale run is not shown either, a bug's class is still logged), and every caller words only a download error as one. `sortOutcome(start, stale?) -> Promise<Outcome>` runs an `ensureRects` call and never rejects: `{kind: "done", done, total, stale}`, `{kind: "failed", facts}` (`downloadFacts` of a download that fell short), `{kind: "superseded"}` or `{kind: "bug", error, stale}` (a caller logs its class only); `ensureRects` itself rejects as before, and a `start` that throws before it returns a promise is a bug, a run that resolves with nothing (a test stand-in) is `done`. The caller's own `stale()` is asked once, after the run ended, because a run can turn stale after `ensureRects` made its last check: a `failed` while stale is `superseded`, `done` and `bug` carry the answer as `stale`, and a `stale()` that throws is a `bug` with that error and `stale: false`. No caller asks `stale()` after the outcome; `suggest.ts` and `routeLocal.ts` call `sortOutcome` on their own `ensureRects` call (not through the index) so a stand-in `streets` with only `ensureRects` still works. A whole run resolves `{done, total}`, and so does one over rects everything of which is held (`done` = `total` = the tiles under them, no report, no request), and so does one whose source threw after every tile it asked for arrived (nothing is missing, so nothing is shown; the error's class and reason alone are `console.warn`ed; a replaced run's failure and the run's own deadline stop are not logged). There is one kind of street answer, the on-foot one: every way the query brings is walked, in both directions; `RUN_HW` and the access filter keep motorways out of the geometry, so there is no `motorway` list and no `walkable`. `rectQuery(boxes)` asks for the geometry and one count that closes the answer, no ID list (the bench cache is keyed on the query text, which `bench/rect-query.test.js` pins; the removed `motorway` list and the removed bike and car modes' lists `bike`, `road`, `car`, `oneWay`, `reverseWay`, `bikeBoth` are no longer asked for or read, and the street cache's key version moved from `3:` to `4:` with the motorway list and from `2:` to `3:` before it, so a phone's old answers are never mixed in; an answer still carries `groups`, always `{}`).
- `streetStore.ts`: what the index keeps. `_read(answer, {x, y})` adds the ways of an answer the index does not hold yet (Overpass answers a whole way to every tile it touches, so a way across two tiles is held once and listed by both), and bumps `version` (also when it throws midway); without its tile it throws a `TypeError`. An expired copy the street cache hands back in its Map alone (the network failed) is read like any answer and covers its tile. It scores ~50 m segments by the share of their ~30 m corridor still fogged; `opts.fogVersion` (a function, `main.js` passes `() => fogMap.version`; none means the fog never moves) is read at each `newAreaM2`: when it moved, every cached share is dropped (`version` is not bumped: a graph stamps `fogVersion()` itself, and a bump inside a read could turn a held graph not-current mid-run), so nothing calls the index when the fog changes. Past 85% of `MAX_SEGS` (`opts.maxSegs` in tests) a read first drops the least recently used pieces (by `x:y`) down to 70%: a piece is used when a read brings it (a street block's unasked tile too) or it lies under the rects of any `ensureRects` call; none under a running `ensureRects` or under a caller's latest `{holdAs}` run (`HOLD_AS.suggest`, `HOLD_AS.route` in `streetGrid.ts`, the one list of names, typed so a misspelt one does not compile; kept until that caller's next run) is dropped, so when everything is protected the cap cuts a way short as before. An evicted piece is not held (`tiles`), so `ensureRects` asks for it again; what eviction reads and writes (`used`, `runs`, `holds`, `wayFrom`, `pieceWays`) is one `evict` object; `wayFrom` (id -> the tile keys whose answer lists the way, and its segments) and `pieceWays` (`x:y` -> ids) keep a way while any piece lists it, and a way no piece lists any more gives its segments back to `segCount`. `snapPoint` rounds a point to the 0.006° cache grid and returns a plain `{lat, lng}` (callers read only those two fields); the index reads nothing from the page.
- `tileStore.ts` / `streetCache.ts`: the street cache. `TileStore` is a key-value store with LRU eviction over the page's IndexedDB (memory fallback when IndexedDB is missing, fails or does not answer within `opts.timeoutMs`, default 10 s; `open` never rejects; `store.backend` is `"indexeddb"` or `"memory"`; the memory store copies values in and out like IndexedDB does). The IndexedDB `get` is a readonly transaction, and rewrites `usedAt` (best effort, behind the read, in its own transaction) only when it is over an hour old; a put that fails with `QuotaExceededError` evicts a tenth of `maxEntries` (16 when unbounded) and tries once more; a connection closed by `versionchange` or by the browser, or dropped after a transaction timeout, is reopened by the next call; a request that succeeds after its open was given up on (blocked, timed out) is closed. Tested against the hand-rolled `bench/lib/fake-idb.js` by `bench/tile-store-idb.test.js`. `StreetCache.create({store, network, now})` wraps a street source: per-tile answers kept 90 days, keys `"4:run:" + x + ":" + y` (`run` names the on-foot answer; entries under `"2:"` and `"3:"` (the old run answers, which carry id lists, and the removed `"2:bike:"` kind) and the unversioned 0.05° keys are never read), each network tile stored as it arrives so a failed run keeps them, a stored answer goes to `onTile` with a third argument `{cached: true}` (a network one with none) and never calls the network, other opts (the run's clock, busy wait and `stale`) go to the network, a store error falls back to the network (one call counts as one failure however many of its reads and writes failed; after 3 such calls in a row the store is skipped for the rest of the session, no read and no write, and one `console.warn` gives the count and `store.backend`; a call that gets through the store resets the count; with the store skipped nothing is there to read, so an outage rethrows the network's error with no expired copy served), an expired copy serves only when the network fails with an outage reason (`busy`, `blocked`, `stalled`, `offline`, `server`, `streets-partial`; any other throw is a bug and rethrows), every tile still missing has one, the run is not stale and the caller did not stop it from `onTile` or its busy wait, and it comes back in the returned Map, never through `onTile`, so the run deadline cannot cut it off. A stored answer with a malformed top level is a miss; one with a non-object way or an uniterable group is a miss and its entry is deleted (fields inside a way are not checked). Serving expired copies after an outage logs one line (count and reason, no tile data). The `4:` prefix of a stored name is also the schema version of a stored entry. `sweepLegacy()` deletes up to 256 entries whose names have no leading version number (numbered entries of any version stay) and never rejects; `main.js` starts it after the store opens, not awaited. A failure rethrows the network's error unwrapped (it needs nothing from `streets.ts`); `ensureRects` counts the tiles. `main.js` opens the store with `maxEntries: 1024`, builds the `StreetIndex` on `overpassFetch`, then swaps in the cache's `fetchStreets` once the store opens. Load order: in `engine.ts`, which loads after the pako tags.
- `elevation.ts`: `Elevation.create({store, fetchTile, decodeTile})` / `Elevation.open()` (IndexedDB `crossfog-elevation`, 200 tiles), `elevationAt([[lon, lat]]) -> Promise<(metres|null)[]>`, `within(promise, ms, fallback)` (the promise's value, or `fallback` once `ms` has passed; a later value is dropped). AWS terrain tiles (terrarium PNG, zoom 12) from the bucket's own host, bilinear between pixel centres, edge pixel clamped at a tile border; a tile that cannot be fetched or decoded gives `null`, never a throw, and logs one line per stage (`fetch`, `decode`) and error class (`elevation tile not loaded, fetch failed: Error`; a name that is no plain identifier is `unknown`, any other thrown non-object, such as a string, is its type), never the message, which can hold the tile URL or number. Only tile numbers leave the page. It reads `fetch`, `createImageBitmap`, `OffscreenCanvas` and `indexedDB` from the page object `pageGlobals.ts` passes it, each when a tile is fetched, decoded or stored, never at load. Built in `engine.ts`. `routeLocal.ts` and the adoption of a suggestion in `main.js` call it.
- `estimates.ts`: `Estimates.estimate(coords, elevation) -> {coords (with z), distanceM, seconds, ascentM, descentM, elevationKnown}`, a port of BRouter's cheap-ruler distance, filtered ascent (10 m buffer; `{ascentFilterM: 5}` is the other value BRouter uses) and walking time model (Tobler), credited in `mobile/licenses/brouter-LICENSE.txt`. A `null` elevation is carried forward (leading ones take the first known value) and `elevationKnown` counts the real heights, so a caller can tell flat ground from heights that never arrived; a non-finite coordinate, a `coords` that is no array, an `elevation` that is neither omitted, empty nor one entry per point, and an `ascentFilterM` that is not a positive number throw `TypeError`; `seconds` is a number for any valid line. `Estimates.climb(heights, opts) -> {ascentM, descentM}` is the filtered climb of heights alone (`suggestPure.ts`'s `statsFromCoords`), `Estimates.routeStats(est) -> {km, seconds, ascent, descent}` the stats object of the route editor (`ascent`/`descent` `null` when `elevationKnown` is 0), shared by `routeLocal.ts` and `main.js`'s `adoptRoute`. Built in `engine.ts`; reads no host. Called by `routeLocal.ts` and by `main.js` when a suggestion is adopted; `suggestPure.ts` takes the filtered ascent and descent of `statsFromCoords` from it.

## Benchmark harness (`bench/`)

Headless Node run of the shipping suggestion code against a real `Sync/` folder in the repo root:

    node bench/characterize.js          # density maps, pick scenario centres
    node bench/run.js [out] [filter]    # run SuggestTool on bench/scenarios.js
    node bench/overpass.js [filter]     # street-network context
    node bench/route-timing.js          # routeWaypoints pin-drag timing on a cached area, offline
    node bench/compare.js <baseline.json> <candidate.json>   # acceptance check, see bench/README.md
    pnpm --dir mobile test:bench                             # every bench/*.test.js, offline (~20 s); `pnpm verify` runs it, and the pre-push hook for a push touching bench/

- A bench test or script requires `bench/lib/host.js` (`window` is the Node global and `L` is `bench/lib/leaflet-stub.js`, which stays until #411 removes the stub) and then `app/src/engine.ts`, and reads the page globals off `global`; a new app module reaches the bench through `engine.ts` and `pageGlobals.ts`. `installTileFetch` in `bench/lib/tileFetch.js` sets the Overpass order to overpass-api.de first, because `bench/cache/` holds answers from that instance (the only bench code that posts to Overpass is the one it installs).
- `bench/lib/headless.js` installs `bench/lib/tileFetch.js` on each run's `StreetIndex`: the Overpass request is the single rect of the run's `ensureRects` call (the `StreetIndex.rectQuery` text, with its `[timeout:25]` read as `[timeout:60]`, is what `bench/cache/` is keyed on), split per tile and handed to `onTile` in the order asked. `tileFetch.js` serves one set of rects per index (a second set that needs a fetch throws, `bench/tile-fetch.test.js`; a suggestion turns that into an `internal` error, which `run.js` counts) and asks only for the rects, so the bench's `covered()` is true over whole tiles that were fetched in part: its scores are not strictly the app's, its graphs are. `bench/run.js` prints the live request count and the number of scenarios that threw or ended `internal`, and exits 1 when either is not 0: a live request means, unless the cache was cleared (then `BENCH_ALLOW_LIVE=1`), that the query text changed, so fix `rectQuery`, do not refetch.
- The bench scores with the page's own fog gain: `bench/lib/fog.js`'s `gainOver(fogMap)` builds it (and `loadSync(dir)` reads a Sync folder), and `bench/fog-gain.test.js` pins it.
- Overpass responses are cached in `bench/cache/` (gitignored); delete it to re-measure live. Overpass answers 502 under load and the run then ends in the error state: rerun after a minute, only failed requests refetch. `bench/cache/brouter/` is leftover from before suggestions went local; only `bench/estimates-cache.test.js` reads it (it skips when absent, `CROSSFOG_BROUTER_CACHE` points it elsewhere) and nothing writes it. The committed estimate fixtures are in `bench/fixtures/brouter/`. The acceptance baseline is the saved `bench/out/baseline-brouter.json`.
- Results go to `bench/out/<name>.json` (gitignored).
