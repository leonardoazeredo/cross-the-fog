# Cross the Fog (Expo app)

Read `AGENTS.md` first: Expo APIs change every SDK, so fetch the versioned docs (`expo` is `~58`, `https://docs.expo.dev/versions/v58.0.0/`) before touching an Expo, EAS or React Native API.

Android only. iOS is paused until the Android phone app and the Wear OS app are done, tested and released: no iOS builds, simulator runs, fixes or plan items before then, and every check runs on Android. `AGENTS.md`'s iOS examples do not apply.

## Commands

- Unit tests: `pnpm test` (vitest, projects `unit` and `adapter`). One file: `npx vitest run test/unit/incoming.test.ts --reporter=dot`.
- Typecheck: `pnpm typecheck` (it runs `pnpm generate` first). Lint: `pnpm lint` (`biome check . ../app/src/*.ts`) or `npx biome check <paths>`; `biome check .` in `mobile/` prints no warning (the `../app/src/*.ts` half of `pnpm lint` still prints unrelated ones), and `biome.json` turns `noNonNullAssertion` off under `test/**` only, so a non-null assertion in `mobile/` production code is a lint warning.
- Full gate: `pnpm verify`.
- Builds: use `pnpm android`; it regenerates the web bundle first. A raw `npx expo run:*` does not.
- Android builds need JDK 21 (`JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-21.jdk/Contents/Home`), `ANDROID_HOME=$HOME/Library/Android/sdk`, and `--device <AVD name>`, not the adb serial.
- e2e builds need `CROSSFOG_E2E=1` for the web build, the app config and the prebuild, and a Release configuration. Run Maestro against them with `maestro --device <serial> test .maestro`.
- Pull requests: `gh pr create --repo leonardoazeredo/cross-the-fog --base main`.
- `../watch/` (the Wear OS app, imported from GlanceMap, ADR 0009; its pin is in `../watch/UPSTREAM.md`) is a separate Gradle project that this app does not build or depend on yet (the shared `../link/` module is the one thing both Gradle builds include). Build and test it from `watch/`, not `mobile/android`: `./gradlew :app:assembleDebug :app:testDebugUnitTest`. The Wear emulator is the AVD `crossfog-wear-os7-test` (Wear OS 7.0, arm64); start it with `-port 5556` beside the phone AVD.
- `modules/platform` (Kotlin local module, hand-written and committed, unlike the generated `mobile/android/`; Gradle runs in `mobile/android` and finds it as project `:platform`). With the Android env above (the scripts below find a JDK 21 and `$HOME/Library/Android/sdk` themselves when `JAVA_HOME` and `ANDROID_HOME` are unset):
  - JVM tests (`KeyWrapTest`, `KekReadTest`, `KeyStateTest`, `DatabaseKeyHexTest`, `StagedActivitiesTest`, `UnsentRoutesTest`, `ModuleFailuresTest`, no device): `pnpm test:android`, which `pnpm verify` runs after the contract check. `mobile/android` is generated and git-ignored, so a fresh checkout or worktree has none: the script runs `pnpm generate` (about 2 s) to make the page, runs `expo prebuild --platform android --no-install` when `android/` is missing or its `settings.gradle` lacks the shared `link/` include that `plugins/withLinkProject.cjs` adds (about 1 to 2 s; prebuild applies the config plugins to an existing `android/` too, so an old generated one gets `:link`, and one prebuilt on purpose, with `CROSSFOG_E2E` say, is otherwise left alone), then `./gradlew :platform:testDebugUnitTest :link:test` in it (about 2 s when nothing changed, 15 to 30 s when the tests run, up to 50 s with a cold Gradle daemon; the first run on a machine with no Gradle cache downloads its dependencies). It fails, never skips, when the JDK or SDK is missing or Gradle fails. Its pure parts are tested by `test/unit/androidEnv.test.ts`.
  - Instrumented tests (`KeysTest`, `KeystoreIdentityTest`, `KeystoreSessionTest`, real AndroidKeyStore and Conscrypt; an emulator must be running, `chase-cashew-test` or `crossfog-phone-test`, an API 36 image made with `avdmanager --sdk_root ~/Library/Android/sdk create avd -n crossfog-phone-test -k "system-images;android-36;google_apis;arm64-v8a" -d pixel_7`, then a smaller `disk.dataPartition.size` set in `~/.android/avd/crossfog-phone-test.avd/config.ini` before the first boot (the default partition did not fit the disk; the emulator raised the 4G written there to the 6 GB it ran with); start it with `-port 5558` and set `ANDROID_SERIAL=emulator-5558` next to another emulator): `pnpm test:android:device` (`connectedDebugAndroidTest`; not in `verify`, and it fails with a message when no device is attached or `ANDROID_SERIAL` names one that is not). They run in the module's own test APK (its own UID, Keystore and `noBackupFilesDir`), so they never touch the installed app's keys.
  - `StagingStoreTest` and `FramesTest` (software key, no device) run under the same `:platform:testDebugUnitTest`; `StagingStoreKeystoreTest` (the real Keystore key) under `connectedDebugAndroidTest`. Set `ANDROID_SERIAL=emulator-5554` when a phone or watch is also attached.
  - Watch app and `:link:test` under the watch build's Kotlin (`:app:testDebugUnitTest :link:test` in `watch/`, which compiles the app's debug sources; no device): `pnpm test:watch`, the last Android step of `pnpm verify` (about 10 to 40 s warm; a cold daemon or an empty Gradle cache is slower and was not measured). `watch/` is committed with its own `gradlew`, so the script neither generates nor prebuilds anything for it.
  - The instrumented tests (`connectedDebugAndroidTest`) do not run in `pnpm verify`; every JVM test above does.
- Kotlin keys: `Keys.databaseKey()` reads `noBackupFilesDir/keys/db.key.v1`; a file without the Keystore alias (or the alias without the file) is `KeyLostException`, and so is an `UnrecoverableKeyException` on the alias that repeats after one retry 200 ms later; JS sees either as `KeyLostError` from `src/platform/platformModule.ts`, the only file meant to import the native module `modules/platform` (nothing enforces it), apart from `src/dev/devActions.ts`, which imports it directly so a static wrapper does not put `stageForTest` in the release JS. `keyState()` reads `fresh` (neither), `lost` (exactly one, or the alias with no Keystore key behind it, `KeyLostException.absent`; an AtomicFile `db.key.v1.new` left by a kill before its rename does not count as the file), `unreadable` (both present, and the unwrap fails for good: `AEADBadTagException`, `KeyPermanentlyInvalidatedException` or a key of the wrong length, `KeyLostException.permanent`) or `existing` (both present and not failed for good: a repeated `UnrecoverableKeyException` or a busy Keystore still reads `existing`, so it may still fail; branch on the `getDatabaseKeyHex` rejection). `keyPresence()` reads `fresh`, `lost` or `existing` from which halves are present, with no unwrap and never `unreadable`; `openHistory` asks it first, reads the key once, and asks `keyState()` (a second unwrap) only when that read fails with both halves present. `keyIsLostOrUnreadable` (`src/db/keyState.ts`) is the one lost-or-unreadable test. `resetKeys` keeps the Keystore `deleteEntry` failure as the cause of the "could not be dropped" exception. Treat "fresh" as safe only when no database file exists. `resetKeys()` drops the Keystore key, `db.key.v1` and a stray `db.key.v1.new` so the next read mints a key; it refuses (`KeyRefusedException`, `ERR_INVALID_STATE`) while `filesDir/SQLite/crossfog.db` or `crossfog.replaced.db` exists or the state reads `existing`, and never touches the staging key. `openHistory` calls it when the state reads `lost` or `unreadable` and no database file exists (#72, #67), and reports `keyLost` for either state when one does.
- Native failure codes (`ModuleFailures.kt`): `getDatabaseKeyHex` answers `ERR_KEY_LOST` (`KeyLostException`; `keyState` turns it into a state and the other key calls never throw it); every call on a key (`getDatabaseKeyHex`, `keyState`, `keyPresence`, `replaceLostDatabaseKey`, `resetKeys`) answers `ERR_INVALID_STATE` (only `KeyRefusedException`, a refused reset or replace), `ERR_INVALID_ARGUMENT` (a malformed key) or `ERR_KEY_UNAVAILABLE` (anything else: a busy Keystore, a failed file write), which `platformModule.ts` turns into `KeyUnavailableError`, never `KeyLostError`. Staging calls answer `ERR_UNREADABLE` (an item that is oversized or does not authenticate: `StagingStore.read` throws `UnreadableItemException` and returns null only for an absent item), `ERR_STORAGE` (any other `IOException`; only its class is logged, since a path names the id), `ERR_STAGING_KEY_UNUSABLE` (`UnrecoverableKeyException` or `KeyPermanentlyInvalidatedException` from the staging key's lookup or first use, on `stage`, `readActivity`, `release` and the outbox's `queue`; fixed text, no cause and only the class logged; nothing is deleted and no new entry is minted, so the staged walks stay and the watch, which gets no confirmation, keeps its copies and retries; `platformModule.ts` turns it into `StagingKeyUnusableError` and `send.ts` words a failed route send with `COPY.stagingKeyUnusable`; the hand-off logs the class only), `ERR_INVALID_FRAME`, `ERR_INVALID_ID` or `ERR_NOT_FOUND`; anything else is rethrown as itself.
- Database key in JS (`src/db/keyHex.ts`): a key is a `DatabaseKeyHex`, a branded string only `checkedKeyHex` (64 lowercase hex digits, else "malformed database key") and `newDatabaseKeyHex(randomBytes)` (32 bytes, wiped after) make; `getDatabaseKeyHex`, `replaceLostDatabaseKey`, `openHistory`'s `openDriver`, `ReplaceDeps` and `createExpoSqliteDriver` take or return it, and the module and the driver check it again at run time. A key that reads but does not open the file (`NotADatabaseError`, a wrong key or a file that is no database, which the driver's main open also throws) reads as `keyLost` through `wrongKeyAsKeyLost` in `createDatabase` on every open; on the first open of a process with a replaced copy beside the live file, that copy is put back and opened before a wrong key is read as `keyLost` (a transient throw leaves both files; see Backup and restore). A close that fails after a failed open or migration logs its error class; the first error is the one thrown.

- Staging: activities the watch hands over wait in `noBackupFilesDir/staging/<activityId>.bin` and queued routes in `noBackupFilesDir/outbox/<routeId>.bin` (AES-GCM under the Keystore key `crossfog.staging.v1`, id as AAD; both are `StagingStore`s). The TS side is `src/link/` over `src/platform/platformModule.ts`; `createFakeWatchLink()` stands in for tests. Like the native side, its `release` refuses an id that is not a UUID ("invalid id"). A route the watch refuses for its content (`itemRefused`, today an unreadable GPX) is set aside and announced as `routeSetAside` at once, only if the queued copy still has the revision that was refused (`OutboxRoutes.setAsideIfOffered`); an edited route stays queued, and a set-aside that throws closes the session `STORE_FAILED` with the route still queued. `stageForTest(offerJson)` is registered only by the `src/debug` source set (the `src/release` twin is empty), so it is absent from a release dex; check with `unzip -p <apk> 'classes*.dex' | grep -a -c stageForTest`. A staged item that does not authenticate or parse (or whose offer names another id) is skipped by `pendingActivities`, never deleted, and counted by `unreadableActivities` (`readStagedActivities` in `StagedActivities.kt`); the hand-off adds the walks whose GPX fails `parseGpx`, `createFlows` sends the total as `unreadableActivities {count}` when it changes (and again on `ready` while above 0), and the History tab says "N walks could not be read." (#79). A staging entry that cannot be used (`UnrecoverableKeyException` from the Keystore read, `KeyPermanentlyInvalidatedException` when a read first uses the key) counts every staged file as unreadable and keeps the files, and nothing mints a new entry over it (#308); any other Keystore failure still rejects the call. A lost staging alias is minted again rather than refused, since refusing would turn away every new walk; `Keys.stagingKey(sealedDirs)` logs a fixed line when it does so while `staging/` or `outbox/` holds a `.bin`, and the old items show in that count (#85). Queued routes sealed under a lost alias are removed, not kept: `discardUnreadableRoutes` (`UnsentRoutes.kt`, the native call of the same name) deletes each outbox item that fails to authenticate, parse or match its name and returns how many it removed; the send flow calls it right after reading the link status (once per `sendStatus`, so per page load; a status that cannot be read leaves the routes for the next load) and adds the count to `linkStatus` as the optional `unsentRoutes` (a positive whole number, absent when none), which the page words as "A route could not be sent. Send it again." (plural: "N routes could not be sent. Send them again."). A delete that fails is logged by class only and not counted, so the next call counts the item once when it goes. Like the staged items, an unusable staging entry (the case above) is not a lost alias: every route is kept and nothing is counted. `UnsentRoutesTest` runs under `:platform:testDebugUnitTest`.

- History store (`src/db/schema.ts`, `src/history/`): `migrate` runs every pending step in one transaction, so an interrupted open (even a killed process) leaves the old schema whole and the next open starts again. Schema 2 keeps an activity's GPX as `activities.gpx_deflated` (zlib BLOB, fflate's `zlibSync`, `src/history/gpxBlob.ts`); `ActivityStore` deflates on `add`, `get` returns the row without its GPX, and `gpx(id)` inflates it on demand. Route GPX stays text. Schema 3 drops `travel_mode` from `activities` and `routes` (activities and routes are on foot only); frames and staged items an older build wrote with a `travelMode` key still parse, the key ignored (Kotlin `Frames`) or stripped (the zod schemas). `RouteStore.list()` returns `RouteSummary` rows, a `Pick` of the named fields (a new route field stays out of lists until it is added there and to each store's `list`), and `markSent` on an id it does not hold throws `UnknownRouteError` (the id is a property, never in the message) in both stores. `test/support/schemaV1.ts` builds schema-1 and schema-2 databases for tests (a restore test copies one in as an old backup, another restores `test/fixtures/history-walk-backup.db`, a schema-1 backup).

- Backup and restore (`src/backup/`, `src/flows/backup.ts`, `src/platform/backupPlatform.ts`): a backup is a SQLCipher file made by `SqlDriver.exportTo` (`ATTACH ? AS backup KEY ?` with both bound, never spliced, then `sqlcipher_export`; key `null` is the plaintext copy after the P5 warning), reopened through `OpenBackup` to add `blobs` rows (`import` = the Fog of World zip, `page_settings` = the page's `f2m_*` keys), saved by the native `createDocument` + `copyToUri`, and removed from the cache in `finally`. Restore copies the picked document into `cache/backup/` with `copyFromUri` (it returns the first 16 bytes: `SQLite format 3` means a plaintext backup, anything else page-aligned may be encrypted), opens it, asks for confirmation, then `createDatabaseReplacer` closes the live database, exports the backup into `crossfog.restoring.db` keyed with the device key (when the key is unreadable and `keyState` reads `lost` or `unreadable`, with a new key, generated in JS, that `replaceLostDatabaseKey` keeps only after the swap and before the reopen, so a failed build leaves the old key and a failed reopen after it is kept leaves the new file live, since the old one opens with neither key; a key that cannot be read while the state reads `existing`, such as a repeated `UnrecoverableKeyException`, ends the restore before the build), checks the counts, deletes the `blobs` rows and `VACUUM`s it (no freed pages keep the zip), swaps files keeping `crossfog.replaced.db` until the new file has opened and migrated; `createDatabase` puts the old file back whenever a swap left no live one, and on the first open of a process keeps the replaced copy until the live file opens: it puts the copy back (deleting the restored file) only on proof this build can never use the live file (from the driver's open or `migrate`): `NotADatabaseError` and `NewerSchemaError` (`migrate`, a schema from a newer app), which are typed outcomes, or an integrity check of the live file that answers "damaged" (`checkFileIntegrity` in `expoSqliteDriver.ts`, run on its own raw connection after any other throw and never decided from the error's wording: expo-sqlite words every SQLite failure as `Error code <n>: <text>`, damage reads as code 11 or the bare code 1 `SQL logic error`, and a full disk or a bug can too). The check opens a new connection, keys it and reads `PRAGMA cipher_integrity_check` (a row per page that fails its HMAC or has the wrong size, e.g. a file cut inside a page; an HMAC failure of page 1 is a wrong key or a page 1 that does not verify, and a wrong key lists every page of a good file, so it is no verdict (`NotADatabaseError`); a row that is neither of the two page reports, such as a failed read or key derivation, is no verdict either) and then `PRAGMA integrity_check` (a single row `ok`; a row for a page it failed to read with a code other than corrupt is no verdict); only "damaged" puts the copy back. A check that cannot run or throws (a file cut on a page boundary: no page fails and `integrity_check` throws `Error code 11`) is no verdict, so with `KeyUnavailableError`, a full disk or a bug it rejects with both files left, and the next open decides again (#346, #363); a failed check logs its error class (`restore integrity-check`); damage the open and `migrate` never read (a data page) is not found at the first open; a put-back logs the error class (`restore put-back`); a key-lost result leaves the copy beside the live file. Restore refuses with `noSpace` (nothing changed) unless the free space is at least 5 times the backup (`RESTORE_SPACE_FACTOR`: the cache copy, the cache zip, the fog store's pending zip, the built file, VACUUM's second copy), checked before the copy against the picker's `size` (`OpenableColumns.SIZE`, when the provider gives it) and after it against 4 times the copied size. A page that does not confirm `applySettings` gives `settingsNotApplied` ("Restored, but the page settings were not applied.", the page still reloads; the failure's class is logged as `restore settings-apply`). `saveFileAs` (backup and Fog of World export) fails when `copyToUri` wrote a byte count other than the cache file's size, or that size is not a positive number. The native `SaveAs.copyToUri` deletes the document the picker created when anything fails (a path refused, `openOutputStream` unavailable, a throw during the copy, or a byte count that is not the source's length), so none of those leaves an empty or partial file in the user's folder; a delete that itself fails is logged by error class only and the copy's own failure is still the one thrown. `saveFileAs` reads the source size before the picker creates the document (a size that is not positive fails with nothing created), and its check on the count covers a count that disagrees with the size read there, the one case that does not delete. A delete that answers `false` (older Android versions and providers do not throw) counts as a failed delete. `SaveAsTest` (instrumented, file:// targets, run by hand: #68) covers each case with the length, delete and report as seams. A restore that cannot replace the saved fog still reloads the page (`fogNotReplaced`), and the controller refuses an import, a clear or a shared file while a restore runs. `createFlows` runs the whole restore under `HandOffFlow.hold`: no watch offer starts, an activity that commits meanwhile keeps its staged copy, and the hand-off runs again when the restore ends. `historyGate` (`src/db/gate.ts`) makes every store call shared and the swap exclusive. The page's settings travel as `needSettings` / `settings` and `applySettings` / `settingsApplied`; the restore waits for the ack before it reloads the page. `NotADatabaseError` cannot tell a wrong passphrase from a file that is no database, so the copy says both. `test/support/nodeSqliteDriver.ts` simulates keys per file path (node:sqlite cannot encrypt): the emulator is the real check, and `head -c 16` of the saved file is `SQLite format 3` only for an unencrypted backup. `createDocument` needs a person at the picker, so `SaveAsTest` covers the two copies on `file://` targets.

- Import copies that did not survive (`src/flows/importFlow.ts`, tested over the real `FogStore` in `test/unit/controller.test.ts`): a `promotePending` that fails after the page's good verdict first has `current()` read: `promotePending` writes the new pointer before it removes the old pointer and `pending.json`, so when the saved fog is already the staged copy (same `sha256` and `savedAt`, the copy read before the promote) the import is reported as done, with the page left as it is, nothing said and `pending.json` and the zips no pointer keeps cleared with `discardPending` (best effort: an old pointer the promote left is removed by the next start's `recover`, and a `pending.json` that stays is dropped by it with the notice that the import failed); otherwise, and when either read fails, it drops the copy with `discardPending`, remounts the previous fog and queues one `COPY.importFailed` for the next `ready`, so `recover` finds no pending copy and says nothing again at the next start; when the remount fails it is a toast instead, and when the discard fails too the toast comes at once and the page is left alone (a remount would serve the copy as pending again and let the page's next verdict keep it), the next start's `recover` dropping it. A page that dies while `pending()` cannot be read has its copy dropped unread (`discardPending` runs anyway), then the same one queued notice, which is also said when that discard fails; a verdict arriving while no import is waiting for one (an import still choosing its file has staged nothing; a copy that could not be dropped, a restore's copy whose promote failed, or one a failed store read left behind, each served again after a remount) discards the copy instead of promoting it (never while a restore runs: the restore owns its staged copy and promotes it itself, so the controller ignores the verdict) and reloads the page onto the saved fog (no reload when the discard fails, which would serve the copy again); both failures log the error class only.
- A restore that fails after staging (`src/backup/restore.ts`, `src/flows/backup.ts`, tested over the real `FogStore` in `test/unit/controller.test.ts`): once the restore has staged the fog store's pending copy, any later failure discards it and throws `RestoreFailedAfterStagingError` (`cause` is the original; a failure before staging, or in a backup holding no import, throws the original). `flows/backup.ts` says `restoreFailed` once, logs the cause's class and returns true, so the controller resets the reload guard and remounts: a page the renderer's death had served the staged copy, which the controller leaves to the restore (`restoring`), would otherwise keep showing a copy that no longer exists, and the reload serves the previous fog. The remount is taken on every such failure, not only when a page was served the copy: a healthy page loses nothing (the saved fog is what it reloads) and the notice is not repeated, as a remount queues none.

- Expo driver queue (`src/platform/expoSqliteDriver.ts`): `exec`, `run`, `all`, `transaction`, `exportTo` and `close` share one queue, because `withExclusiveTransactionAsync` uses its own connection and a plain query beside it fails with "database is locked"; a transaction callback must query only through its `tx` (a call on the driver from inside it waits on its own transaction forever, undetected), and a hung callback stalls every query. The node test driver does not queue plain queries.

- Backup passphrase rules: the backup dialog (`src/ui/passphraseForm.ts`) rejects a passphrase under 8 characters and one of the form `x'<64 hex>'` or `x'<96 hex>'` (any case; SQLCipher takes it as the raw cipher secret, with no derivation step), both with plain copy; a restore accepts any non-empty text.

- Exports (`src/flows/exportFlow.ts`, `src/platform/{zipWriter,exportFiles,crashLog}.ts`, page: `fowExport.js`, `exportWarning.js`): the page writes the Fog of World tiles and sends them as `exportBinary` chunks (1 MiB raw at most, `exportId` is `[A-Za-z0-9-]` and `name` is `[a-z0-9]`, both because they become path segments; `files` is the count of files in the export, at most 65534, one under the ZIP64 sentinel). `createExportFlow` queues the chunks (WebView messages are not serialized, so "every file is complete" is seen once), keeps parts under `cache/export-<exportId>/parts/<name>/<index>`, joins a finished file into `Sync/<name>`, and when all `files` are in writes `Sync.zip` with `writeZip` (stored, fixed 1980 date so the zip's own headers say nothing about when it was made; the suggested file name still carries the day), saves it with `saveFileAs` (`createDocument` + `copyToUri`) and removes the directory in `finally`; a cancelled picker says nothing, a disagreement between chunks or any error drops the export with a message that carries no path and logs the stage it failed in (`failed while receiving|assembling|zipping|saving`, then the class). The page is told each outcome as `exportStatus {exportId, state}`: `saving` just before the picker opens, then `saved`, `cancelled` or `failed` (`FowExport.button` in the page holds its button until one of the last three). An export with no chunk for `EXPORT_IDLE_MS` (60 s, armed after each handled chunk and run through the queue, so chunks still queued re-arm it first) is failed and its directory removed, with the fixed log line `export idle, dropped`; `abandon(exportId)` (a chunk of it failed the bridge's schema) does the same, and is a no-op for an export already finished or failed. Up to 256 finished or failed ids are remembered, so a late chunk does not start an export again. The next start removes any `export-*` directory (`ExportFs.removeExportDirs`) and `cache/exports/` (`clearShareCopies`). `exportFiles.ts` refuses a cache path with an empty, `.` or `..` segment, and `writeZip` an entry name with one (a leading `/` included) or a repeated name. `test/unit/bridge/exportLimits.test.ts` ties the page's `CHUNK_BYTES` to `EXPORT_CHUNK_BYTES`, `EXPORT_MAX_FILES` to `zipWriter`'s `MAX_ENTRIES`, and checks that Fog of World's tile names pass the chunk schema. `shareExport` (GPX) deletes its cache copy as soon as `shareAsync` returns or fails. `scrubCoordinates` in `crashLog.ts` replaces every decimal number with three or more places by `[n]` and every `file://` or `/data`, `/storage`, `/sdcard`, `/mnt` path (which carries the export id) by `[path]`, in the message and not in the timestamp that has three decimals itself. A throw from `status` or `notify` is logged by class and changes nothing (a saved export stays saved, a failed one is still removed). `removeExportDirs` tries every entry and rethrows the first failure, so the log names its class. Every cleanup (`clear`, the `finally` after a save, `clearShareCopies`, `shareExport`'s delete) logs only an error class and never turns a saved export into a failed one. The page's console lines print the reason or the error class only; `bench/export-warnings.test.js` scans `app/src/*.js` for a `console.*` call that names `why`, `explain`, `lat`, `lng`, `coords` or the like.

- Off-origin navigation: react-native-webview is deliberately unpatched and fails open when `decideNavigation` answers late, so the page must make no navigation but a link click. `test/adapter/links.test.ts` scans `app/index.html`, `app/src/` and `app/vendor/` for `<form>`, a `location` assignment, `<meta http-equiv=refresh>`, `formaction` and `.submit()`; a hit in vendored code is not patched but allowlisted in that test's `ALLOWED` with the reason it cannot leave the origin (none today). `installLinks` (`web-adapter/links.ts`) lets through only a `blob:` download and a link whose path and query equal the document base's and that carries a fragment (`href` starting with `#`, or a non-empty hash; `href=""` or `"?"` is a reload and is stopped); every other same-origin link, whatever its `target`, is `preventDefault`ed and opens nothing, so it never reaches the late native answer. `window.open` and the click path share one resolver (`new URL` against the document base: `HTTPS://x` and `//x` open outside, an empty URL or a relative one on the origin does nothing), and `auxclick` is handled for the middle button only. `openExternal`, and the `external` navigation and `onOpenWindow` paths (`createLinkHandlers`, `src/bridge/linkHandlers.ts`, used by `WebShell.tsx`), go through `openLink` (`src/bridge/openLink.ts`): a rejected `Linking.openURL` logs the error class only and shows `COPY.openLinkFailed`, never the URL.

- Native-to-page messages: every one goes through `createSend` (`src/bridge/send.ts`), never a bare `postMessage`. It posts and then schedules a no-op `setTimeout(0)`. Expo Modules v2 (expo-sqlite, expo-crypto; `ReactJSScheduler.post` in `expo-modules-v2-react`) settles promises with `runOnJSQueueThread` plus a microtask drain, outside React Native's RuntimeScheduler. A WebView command issued there waits in the scheduler's rendering updates until the end of the next task, so without the timer it reached the page only when the page next posted (#139). A microtask does not release it; only a new task does. A debug build can hide this, so check native-to-page changes on a Release build (`.maestro/history-release.yaml`).

- Page-to-native messages: `WebShell` gives the WebView's `onMessage` to `createWebMessageHandler` (`src/bridge/webMessage.ts`, tested in `test/unit/bridge/webMessage.test.ts`; `webShellSource.test.ts` reads `WebShell.tsx` for the wiring), which ignores another origin and checks each message with `inspectWebToNative` (`src/bridge/protocol.ts`, which builds its two unions from the tables of `src/bridge/messages.ts`: one entry per message type, `loaded` with its two shapes in the order a tie is decided); a message that fails the schema goes to `reportDropped` (`src/bridge/dropped.ts`). A throw or rejection from the reply (`send`), from `abandonExport` or from the controller's `onWebMessage` is caught in the handler and logged by class only (`warnClass`, `bridge … failed`), so nothing escapes the WebView event and no rejection goes unhandled; which messages are dropped or answered does not change. `DroppedMessage` is a union on `type`: `paths` (readonly zod issue paths, never a value) on every member, `routeId` on `sendRoute` (answered `failed`, with no revision), `exportId` on `exportBinary`, `activityId` on `needTrack` and `deleteActivity` (each null unless that id is itself valid), and for a message with no known type `type: null` with `reason` `json`, `not-object` (an array too) or `unknown-type`. `reportDropped` logs the type, or `unknown:<reason>`, and the paths, and answers: `sendRoute` with `routeStatus failed`, `deleteActivity` with a `notice` (`COPY.activityDeleteFailed`; the card has closed and the row stays, so no fresh list is sent), `needTrack` with `trackUnavailable` `readFailed`, and `exportBinary` by abandoning that export, which answers `exportStatus failed` unless the export already finished or failed. A `needTrack` that passes the schema always gets an answer: the track, or `trackUnavailable` (`notFound`, `readFailed`). A drop with no valid id gets none, so the page also times out the track request and the route send on its own (`REPLY_TIMEOUT_MS` in `app/src/history.js`), and the export (`REPLY_MS` in `app/src/fowExport.js`). `parseWebToNative` lives in `test/support/parseWebToNative.ts` (tests and `scripts/web/contract.ts`).

- `window.CrossfogPage` has one declaration, `web-adapter/crossfogPage.d.ts` (`CrossfogPageApi`, `RevealRules`; the page itself is not type-checked): `history.ts`, `loader.ts` and the history test use it, and `scripts/web/contract.ts` derives from it the leaf paths its field list must name, so a field added to the interface without a path there, or a path the interface lacks, fails `tsc`.
- Import outcome (`web-adapter/loader.ts`): the page counts the tile files it could not decode and publishes the count of its latest import as `CrossfogPage.lastImport.corrupt`; the loader hook reads it once the unzip is done (a page that publishes none counts as no damage). A load with decoded tiles and damaged ones settles `{ok: true, tiles, corrupt}`, the count staying on the adapter side because the page already tells the person; a load with damaged tile files and none decoded settles `{ok: false, reason: "corrupt"}`, which the `loaded` message carries (one more value of its `reason` enum) and `importFlow` words as `COPY.damagedBackup` instead of `COPY.notABackup`, since a backup whose tiles are unreadable is not "not a backup".
- Flow failures: every flow and the import log through `warnClass` (`src/flows/warn.ts`, the error class only). A history list that cannot be read sends `notice` `COPY.historyListFailed`, since the page keeps its last list (a deleted row included), except for `HistoryKeyLostError` (`src/db/openHistory.ts`, what `historyStores` throws while the key is lost; the startup alert already said so). `ImportFlow` does not reject on a store, picker or remount failure: a store failure ends any import it started, clears busy and says `COPY.importFailed` (a share that fails before it takes the import leaves a running one alone), with no remount after a failed promote or discard (a discard that failed would hand the page the same bad copy again). The controller's own store reads (`ready`, `needBytes`, `loaded`) are guarded too: a failure is logged by class and `ImportFlow.fail()` ends an import that is waiting for the page's verdict (busy cleared, `COPY.importFailed`, a queued share handed over); an import still picking or being taken is left alone and with none running nothing is said. The import flow queues a notice (`queueNotice`, shown at the next `ready`) only when a `ready` will follow; its other failures are toasts (`notify`). The history may reach the page before or after the fog's `loaded`; the page's `FogMap` merges activity cells and imported tiles in either order (`bench/fog-map.test.js`).
- Page API (`web-adapter/pageApi.ts`): `PAGE_EVENTS` is the one list of native-to-page events; `isPageMessage` is what `session.ts` routes by, so a new event is added there only and the session cannot forget to route it (the page still needs its forward to `window.CrossfogPage` in `web-adapter/index.ts`, as `exportStatus` has; `test/adapter/index.test.ts` boots `index.ts` and checks the `trackUnavailable` and `exportStatus` forwards and the panel's track ask counted, with `@noble/hashes` aliased to a stub in `vitest.config.ts`). The history sync (`web-adapter/history.ts`) counts the track asks open per activity id: its own and the History panel's (`index.ts` wraps `window.crossfog.needTrack` to call `trackAsked`), and takes only the answer that ends the count, because chunks carry no request id and an older copy still in flight would otherwise be revealed and cached under a newer stamp; the phone is assumed to answer in the order asked, a late answer may be dropped and asked for once more, and a silent-forget or a `trackUnavailable` starts the count over. `PAGE_EVENTS` is the keys of `PAGE_MESSAGES` (the page half of the app-to-page table in `src/bridge/messages.ts`), `PageEvent` is derived from it, and the listener sets are typed per event, so `on` and `emit` need no cast. A route the page sends is bounded: `gpx` 10,000,000 characters, 100,000 coords, 500 waypoints; export chunk data is padded base64 of at most 1 MiB decoded.
- One import at a time (`src/flows/importFlow.ts`): a share checks `importActive` before and again after its store read and replace question, so a pick (or another share) that started while the question was open makes the share wait in `pendingShare`, which `endImport` takes next and asks about again; cancelling the question queues nothing, and a pick or share that ends without a verdict (picker cancelled, not a zip, the import could not begin) hands a waiting share over the same way. Only the share that reaches the queue last is kept (an older share confirmed after a newer one queued replaces it), and the one it replaces has its cached copy released at once.
- Shared cache copies (`src/flows/importFlow.ts`): the share intent names its cache copy after the file, so two shares of one file are one path and `releaseSource` on it deletes both. Every share the flow takes in (and a picked file once its import starts) holds its uri in `holders`, and `release(file)` deletes the file only when the last holder has released: the running import's release after `beginImport`, a cancelled replace question, a failed `beginImport`, a replaced queued share and a queued share dropped by `processGone` all leave the file while another share of it is waiting or being read. A release is once per share (a second one for the same share changes nothing), and a share that is never released would keep its file, so every exit of `handleIncoming` and `doImport` releases. The controller turns a share away during a restore through `importFlow.refuse(file)` (it holds the share, then releases it), not `deps.releaseSource`, because a share of the same file can be waiting on its replace question when the restore starts. The cache copy's name is the library's, so it is not made unique here.

## Page bundle

The page's TypeScript modules (`../app/src/*.ts`, imported by `engine.ts`, the one `.ts` script tag) are bundled into `generated/web.ts` by `scripts/web/bundleModule.ts`, which fails the build when an input is outside `app/src/`; `tsc` checks them through the tests that import them (`allowImportingTsExtensions` is on for that). `generated/web.ts` and `generated/licenses.json` are generated and git-ignored; `pnpm generate` writes them (`pnpm android`, `pnpm verify`, `start` and EAS's post-install run it first, but a raw `npx expo run:android`, a bare `tsc` or `knip` on a fresh clone need it run by hand). An e2e build (`CROSSFOG_E2E=1`) writes the e2e flavour into `generated/web.ts`, which contains the developer-only "Dev: drop fog cache" button, so run a normal `pnpm generate` (or `pnpm android`) before a normal build. Stage files by name, never with `git add -A`.

## Build and Maestro gotchas

- `plugins/withReleaseBundleInputs.cjs` adds a Gradle `generateCrossfogPage` task (`pnpm generate`, with `app/`, `web-adapter/`, `src/` (the adapter imports from it), `scripts/`, `licenses/` and `CROSSFOG_E2E` as inputs) that the bundle tasks depend on, so a release build after a page edit holds the edit with no `--rerun` and no `rm -rf` of the bundle output, also from a raw `gradlew` or `expo run:android`; `pnpm` must be on the PATH Gradle runs with. To check an APK holds a change, grep its bundle: Hermes keeps some strings as UTF-16, so use `grep -a -c -P` on the spaced form.
- `android-mcp`'s device-side helper holds the UiAutomation connection, so Maestro fails with "Android driver did not start up in time". Kill the `com.wetest.uia2.Main` process on the device before a Maestro run; the next `Snapshot` restarts it.
- Maestro reports off-screen web view text as visible, so do not guard a swipe with `notVisible`. Use a fixed swipe, and assert that the app was left with `notVisible: "Expand or collapse panel"`.

## Tools

## Commit hook

A hook blocks `git commit` while comment-like lines are unreviewed (markdown, text and lockfiles are exempt). A new Maestro flow with no `#` lines still needed a review (probably because of the YAML `---` separator, which starts with `--`). Finish the edits, run the `pr-review-toolkit:comment-analyzer` agent alone with the first prompt line exactly `Repository: /Users/leo/Lab/defog`, wait for its report, re-run it if you changed a comment, then commit in a following turn. Do not bypass the hook.
